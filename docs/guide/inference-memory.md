# RKNN 推理内存生命周期

Kit 的默认静态图像路径使用 ctypes/DMA；静态单输入特征张量也可使用 ctypes，
通过普通张量协议传输。多个输入、不满足 ctypes 条件的模型，以及显式
`ESK_RKNN_BACKEND=rknnlite` 使用 RKNNLite 兼容路径。两条路径
都必须在实际持有模型的进程中管理内存，应用进程的垃圾回收不能清理推理服务的堆。

## RKNNLite 的循环引用

历史提交 `db282c8` 绕过 RKNNLite 包装层，随后 `125cdc9` 将根因纠正为
ctypes 缓冲区的循环引用，而非已证明的厂商 C 层缺少 `free`。Python 自动 GC
主要按对象数量触发；一个很大的张量可能只有少量 Python 对象，因此等待自动
回收时，驻留的张量字节就可能先耗尽设备内存。

2026-09-24 在 RV1126B / RKNNLite 2.3.2 上，用设备已安装的 SenseVoice 模型
进行了连续调用：输入为固定 float32 `[1,344,560]`，输出 `[1,344,25055]`
共 34,475,680 字节（约 32.88 MiB）。默认回收情况下，推理间匿名内存约每次
增加 34 MiB，测试进程 RSS 从约 216 MiB 增至 585 MiB；达到预设安全余量后
主动回收，RSS 降到约 183 MiB。后续每次回收的 24 次对照保持在约 184 MiB。
测试未故意触发内核 OOM，也没有关闭默认 GC 来制造增长。

本地直接推理仍由 `kit.runtime.rknnlite.RknnLiteRuntime` 保护：

- 返回独立的 NumPy 输出副本，保持 dtype、shape、张量次序和数值；消费方丢弃
  输出时即可由引用计数释放，不再把厂商输出缓冲区的引用环交给应用持有。
- 在返回前丢弃厂商输出引用并执行完整循环回收，初始化和异常返回也执行回收。
- 释放模型成功后清除 RKNNLite 仍保留的模型文件字节，并回收循环对象；释放失败
  则保留模型状态，继续走原有隔离和重试流程，不能提前释放 NPU 所有权。
- 覆盖普通本地 RknnSession/RknnModel 和本地 SenseVoice 后端。
  测试/厂商显式注入的 `runtime_factory` 仍由调用方负责其自定义实现。

这会给本地 RKNNLite 路径增加输出复制和回收开销。ctypes 路径不执行这些兼容操作。
合入 float 特征支持后，单个静态 uint8/int8/float16/float32 非图像输入（例如
float32 NTF 语音特征）可使用 ctypes 的普通 IO；图像快速路径仍要求调用方提供
uint8 NHWC。多个输入仍需 RKNNLite。服务在 auto 模式对未声明输入的模型先检查
图结构；不支持的图在确认上下文已安全释放后回退，不能吞掉驱动初始化或释放错误。
未声明输入的图像模型保留 RKNNLite 兼容行为。应用自己导入厂商 RKNNLite 的
调用不经过 Kit 保护；托管应用应使用模型工厂或 RemoteRknnSession。

状态接口使用 `ctypes` / `rknnlite` 标识实际后端。

## 共享服务的无额外输出复制路径

`inferenced` 使用私有适配层保留厂商输出，普通张量协议直接序列化这些数组；
不再为了 GC 额外复制一份 NumPy 输出。客户端收到的数据仍由其接收缓冲持有，
不改变 socket 协议、数值、dtype、shape 或调用方输出生命周期；这不等于消除
socket 传输自身的复制，也不改变共享 DMA 的借用与复用规则。

- 连续 RKNNLite 调用：下一次推理在取得 NPU 驱动锁之前回收待处理的循环对象。
  已经由空闲维护回收完毕时，不重复执行完整 GC。
- 响应发送结束（包括发送失败）后，先清空线程中的输入输出引用，再通知回收器。
  调度任务也在丢弃自身引用后通知，覆盖请求超时返回、后台推理仍未结束的情况。
- 回收器合并通知，首次通知后 0.5 秒到期，后续通知不会反复推迟期限；服务接受连接
  的循环每至多约 0.5 秒检查一次。空闲时通常约 0.5–1 秒完成末次回收，驱动忙碌、
  GC 自身耗时和系统调度会延迟实际执行，不是实时保证。无需额外线程或逐请求定时器。
- GC 与本进程的原生操作串行，空闲维护不会等待忙碌的驱动。后续普通推理或 DMA
  推理也会处理已到期的旧 RKNNLite 清理，避免只有图像模型继续运行时遗漏回收。
  [多模型并发](inference-concurrency.md)启用后，不同上下文共用读侧执行屏障；
  显式完整 GC 使用独占屏障，等待在途原生调用结束，并阻止新调用使回收饥饿。
- 初始化、卸载及其异常也执行回收，正常服务路径在释放 NPU 驱动锁后进行。释放
  失败仍保留上下文、模型数据和原有隔离策略；自定义注入的后端遵循其自身契约。
- ctypes-only 工作负载不产生 RKNNLite 清理请求。本地直接推理仍使用上述复制
  包装器，不改变已返回结果在后续调用和释放后的有效性。

GC 作用于服务进程的不可达循环对象，不按模型名称释放内存。仍被发送线程持有的
另一模型输出不会被回收；DMA 缓冲仍由模型和客户端通道显式持有、显式释放。

## 服务线程中的大张量

调度线程完成任务通知后清空自己的 job/result 局部引用，结果仍由等待的客户端
任务持有。连接线程发送响应及 FD 完成后清空本轮请求、输入和输出，然后才等待
下一条消息。共享 DMA 缓冲区仍由模型/连接生命周期管理，不随一条消息释放。

这两处修正处理的是强引用滞留：仅调用 `gc.collect()` 无法回收仍被线程引用的
对象。旧代码中 8 MiB 测试输出在模型卸载和客户端断开后仍由工作线程保留；新
回归用弱引用检查连接空闲时输入输出已释放，且客户端收到的结果仍有效。

## 集成与验收

部署最初的生命周期修复需要同时更新固件中的 Kit 和 `market/inferenced`，然后
重启推理服务及依赖应用。本次取消服务端额外复制的优化仅改变 `market/inferenced`
（包括新私有模块 `_memory.py`），要求已有包含保护包装器的 Kit 版本。
仅更新某个应用的私有 venv 无法修复平台共享服务；仅更新 Kit 也不包含服务线程
的引用释放修正。现有应用无须更改 infer 调用、模型格式、权限或安装包接口。

验证应分别记录预热后 RSS/PSS/匿名内存、模型调用数、FD 数量、闲置和卸载后的
残留，并核对输出数值。应设置可用内存安全余量，分别覆盖大输出连续调用、重复
加载/卸载、调用失败、多输入及原图像 DMA 路径。内存稳定平台与线性累积应区分；
分配器保留少量高水位内存不等于泄漏。短时对照不替代 24 小时真实音频验收。

AppMgr 的[内存保护](memory-protection.md)仍作为异常应用和其他资源增长的兜底。

### 2026-09-24 RKNNLite 修复后目标板对照

以下数据来自合入 float ctypes 支持、取消服务端额外复制之前的 RKNNLite 路径；
不代表更新后 auto 模式语音模型的耗时，也不能把 139 ms 全部算作取消复制的收益。
选择 ctypes 后不会发生这里测量的 RKNNLite 输出复制和 GC。

在同一台设备保持 depth-estimation、fall-detection 两个 ctypes 应用运行，另起
使用正式服务实现、真实授权校验和同一 NPU 驱动锁的独立语音测试服务。临时授权
目录/socket 与正在运行的系统服务隔离；模型仍经已安装 manifest 的哈希校验。

- 3 轮每轮 40 次，共 120 次推理，输入与修复前对照一致。120 次输出 SHA-256
  均等于修复前结果，张量大小和形状不变。
- 语音测试服务预热后 RSS 约 187.5 MiB，未随推理次数累加。三轮模型卸载后
  RSS 均为 61,636 KiB（约 60.2 MiB），PSS 约 46.3 MiB；加载期间 FD 为 12，
  每轮卸载回到 6，无逐轮增长。闲置时同样没有留下上一轮大输出。
- 另一次 12 次调用的耗时分解（去掉首轮）中，厂商调用耗时中位数约 858 ms，
  输出复制和完整 GC 约 139 ms。NPU 驱动锁等待另计，不计入这 139 ms。
  这是该大输出模型和当时并发负载下的数据，不是所有模型的固定开销。
- 主机端 Kit、SDK、RGA、推理服务及 AppMgr 回归为 2093 项通过，另有 42 个
  subtest；两个 wheel 的构建/隔离安装检查通过，并验证新模块被包含在 Kit 包中。
- 正式系统服务更新后，原语音应用两轮启动/停止正常，第二轮实际完成 2 次
  推理且无失败，停止后模型引用清零。两个图像应用保持正常运行、推理失败为零，
  最终恢复原先两个图像应用运行、语音应用停止的状态。

这是针对已复现原因的工程验证，尚不代表已完成 24 小时真实音频长稳测试。

### 取消服务端额外复制后的验证范围

主机回归为 2676 项通过、139 个 subtest 通过，15 项因缺少发布工件、相邻训练
仓库或可选依赖跳过。新增 16 项测试使用真实 ctypes 循环缓冲与线程/socket，覆盖
输出对象身份、多模型持有、慢速发送、空闲、异常、卸载失败、超时后后台完成、
回收通知合并和服务关闭；固件暂存测试核对新增 `_memory.py` 随源码安装。

2026-09-24 又在另一台 RV1126B / RKNNLite 2.3.2 设备完成以下真机对照。设备
原有 PP-OCR 应用一直运行；测试服务使用当前源码、私有 socket/授权目录和正式
服务相同的 NPU 驱动锁。测试模型放在临时应用根目录，仍经过 manifest、模型
SHA-256、进程身份校验。共核对 192 个基线/候选源码文件的哈希；没有替换正式
服务或安装语音应用，因此这项测试验证推理服务，不涵盖真实音频采集和识别流程。

- 强制 RKNNLite：新方案 3 轮、每轮 40 次 SenseVoice 推理，共 120 次；穿插
  24 次 OCR 识别模型调用。所有语音输出与先前复现输入对应的 SHA-256 完全
  相同，OCR 输出也与复制方案一致。跨调用保留的客户端结果未被后续推理改写。
- 刚完成语音推理时，服务通常暂留约 32.88 MiB 厂商输出；后续调用或空闲回收
  将其释放，没有按调用次数累加。三轮空闲 2 秒后的 RSS 分别约 195.6、197.3、
  197.3 MiB；卸载后分别约 61.9、69.9、69.9 MiB。第二轮出现约 8 MiB 的
  内存高水位保留，第三轮相同，不能把一次分配器高水位直接算作泄漏，也不能
  仅据三轮测试排除长期缓慢增长。每轮加载期间 FD 为 19，卸载回到 7，包含
  测试日志文件描述符。
- 慢速接收：暂停读取 33 MiB 语音响应，让服务端发送阻塞，同时执行 8 次
  另一模型推理及 GC，随后收到的语音输出哈希仍一致。另测错误 dtype 拒绝后
  继续调用、真实推理期间客户端断连；空闲后大输出回收，服务继续正常推理。
- 默认 auto：语音使用 ctypes 普通张量 IO，OCR 使用 `rknn-dma-v1`；官方
  `multiple_input_demo.rknn` 双输入图自动回退 RKNNLite。三种路径在同一服务中
  交替执行 10 轮，输出均与基线一致，双输入模型返回 `[1,8,128,128]`。
- 原有系统服务和 OCR 应用的 PID 未变化；系统 OCR 检测调用数从 14886 增至
  17477，识别调用从 256 增至 270，两个模型失败计数始终为 0，没有新增 OOM
  记录。测试后退出全部临时进程并删除临时模型、授权、socket 和源码目录。

同机相同双模型工作负载下，复制方案 25 次和新方案 120 次语音调用的对照
（每轮剔除前两次预热）如下，单位为毫秒、中位数：

| 测量范围 | 复制方案 | 服务无额外复制 |
| --- | ---: | ---: |
| 厂商 inference 调用 | 893.2 | 887.0 |
| 调用线程内完整 GC | 84.4 | 108.1 |
| 服务 backend.infer（含驱动锁等待、GC） | 1036.8 | 1002.4 |
| 客户端 infer 往返（含张量传输和接收） | 1204.8 | 1171.5 |

没有额外数组复制，但仍需完整 GC，空闲维护 GC 也可能在调用线程之外执行。

139 ms。实际收益受输出大小、GC 对象图、系统负载和温度影响；表中各项中位数
不能直接相加。这些短时功能、内存和耗时对照通过，24 小时真实音频长稳验收
仍需单独进行。
