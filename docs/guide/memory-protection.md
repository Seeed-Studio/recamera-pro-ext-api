# 应用内存监控与保护

本功能由固件中的 AppMgr 持续运行，不依赖浏览器页面是否打开。
它用于在内存紧张时降低负载、保存诊断信息、恢复退出的共享推理服务，
不能替代应用、RKNN runtime 或驱动本身的泄漏修复，也不是 cgroup 硬隔离。

## 统计口径

- 系统使用 `/proc/meminfo` 的 `MemAvailable`，不把可回收缓存直接当成泄漏。
- 应用统计经过身份校验的主进程、进程组及子孙进程，采集 RSS、匿名内存和 PSS。
  PSS 按比例计算共享页面；不可读时趋势退回匿名内存，不将采集失败当作零。
- `inferenced` 独立统计。模型状态增加 `backend` 与 `owners`
  （应用、实例、代次），便于区分 RKNNLite 与 ctypes 路径。
  `memory_reserved_mb` 仍是模型准入估算，不等同于实测占用。
  部分驱动/DMA 分配不计入进程 PSS，所以还需同时观察系统可用内存。
- 正常每 5 秒采样，接近压力阈值时每秒采样；PSS 和模型清单每 15 秒更新。
  每个当前实例最多保留 145 个内存点，接口下采样至最多 49 点；历史不持续写入闪存。
- 进程更换、应用代次变化、共享服务模型集合变化，都会重建增长基线。
  默认预热 120 秒，再观察至少 300 秒，净增长达到 64 MiB 且三个时间段均增长，
  才标记“持续增长”。该标记不是已经证实泄漏。

## 默认策略（2 GiB 设备）

| 条件 | 行为 |
| --- | --- |
| 只有内存增长、系统可用内存充足 | 显示增长提示，继续观察 |
| 可用内存低于 320 MiB 持续 30 秒 | 暂停新增启动、重启、上传和安装，返回 `memory_pressure` 或 `memory.pressure` 等待状态 |
| 低于 256 MiB 持续 10 秒 | 优先停止持续增长的应用；共享推理服务增长时，逐个停止其依赖应用释放模型 |
| 低于 128 MiB | 紧急减载，按平台优先级和实测占用选择一个托管应用停止；不把这种选择标成“确认泄漏” |
| 可用内存已低于 384 MiB，且近期快速下降 | 最近 3–15 秒下降至少 64 MiB、按当前速度预计 10 秒内降至紧急阈值时，提前执行紧急减载 |
| 停止后 | 等待新采样重新评估，普通保护间隔 20 秒，紧急状态最短 5 秒；不会在一次循环中批量停止所有应用 |
| 高于 384 MiB 持续 60 秒 | 解除新增负载限制；保护停机的应用仍须手动启动 |

使用现有 Coordinator/Supervisor 停止流程：先持久保存停机意图和原因，
再通知应用退出，清理准确代次的模型授权、子进程、资源占用和结果来源。
超时仍由原有强制停止逻辑处理。不会修改应用包的 `memory_mb` 含义，
不会因为超过声明预算就直接杀进程。

默认应用优先级相同。管理员可通过 AppMgr 服务环境变量
`APPMGR_MEMORY_APP_PRIORITIES='{"important-app":200,"optional-app":50}'`
调整压力减载顺序，数值越大越晚停止。包作者不能通过 manifest 修改这个平台策略。
固件内置推理及 AcousticsLab 等系统服务不在此自动停止范围内。

阈值和时间可通过 `APPMGR_MEMORY_` 加 `Policy` 字段的大写名称设置，
例如 `APPMGR_MEMORY_CRITICAL_MB=128`、`APPMGR_MEMORY_WARMUP_SECONDS=120`。
必须为有限正数，且 `critical_mb < low_mb < warning_mb < recovery_mb`；
错误配置会明确报错，不能用零关闭保护。

## 共享推理服务恢复

`S93inferenced start` 创建 `/run/recamera-inferenced.enabled`，`stop` 删除它。
服务死亡而启动意图仍存在时，AppMgr 连续观察至少 10 秒后：

1. 持久保存恢复次数和故障快照。
2. 将依赖共享推理服务的托管应用置为保护停机，完成旧代次清理。
3. 调用 `S93inferenced recover`，重新验证启动意图，并执行停止/启动及协议就绪检查。

恢复预算为每 10 分钟最多 3 次，重试有 30/120 秒退避，记录跨 AppMgr 重启保留。
应用不会因服务恢复就自动重新启动，避免立即复现 OOM。
服务内存持续增长且客户端已经全部停止、压力仍未解除时，也可受控重启服务。
手动 `stop` 不会被监控程序撤销；正常退出的 CPU 应用与系统服务不被连带重启。
启动脚本使用 BusyBox 兼容的文件锁，避免运维操作与自动恢复同时执行。

这不是进程硬内存上限：突发的大量分配、不可回收驱动内存，或其他不受管理的
进程耗尽内存，仍可能先触发内核 OOM。将来启用 cgroup memory controller 时，
可再增加每应用的硬隔离；当前不依赖设备未启用的 cgroup/PSI 接口。

## API、界面与诊断

- `GET /api/app-center/v1/resources` 的 `memory_guard` 返回系统、各应用、推理服务和压力状态。
- `GET /api/app-center/v1/apps` 的 `apps[].runtime.memory` 返回应用内存趋势、共享服务内存、
  系统可用内存及 `protection`。`stale=true` 时不能作为实时数据使用。
- `protection.reason` 分为 `app_memory_growth`、`shared_inference_pressure`、
  `system_memory_pressure`、`inference_service_lost`。后两者不能用来认定某应用泄漏。
- 应用中心卡片显示保护原因和时间，运行详情显示内存统计与趋势；旧固件缺少字段时兼容隐藏。
- `/userdata/local/appmgr/memory-incidents.json` 仅保存最近 20 次保护/恢复事件及采样快照。
  `/userdata/local/appmgr/inference-recovery.json` 保存恢复预算。
  内核 OOM 日志仍需结合 `dmesg` 检查；文件存在的 socket 不是服务健康证明。

## 固件集成与验收

从源码构建并同时集成 `market/appmgr`、`market/inferenced`、`S93inferenced` 与前端。
`tools/install_platform_services.py` 会包含新增模块。单独更新 Kit wheel 不会安装这套保护。
正常固件启动会创建服务启动意图标记；旧版本服务热更新必须经过新版启动入口，
不能仅复制 Python 文件后假定存在启动标记。

回归应覆盖：健康并发应用、冷启动模型加载、反复安装/启动/停止、应用子进程、
PID/代次变化、共享服务退出、显式停止服务、恢复预算、内存恢复滞回、停机原因跨重启保留。
压力测试应先使用受控阈值或模拟采样验证，避免主动将设备推入真实 OOM。
长期验收至少运行 24 小时，保存系统/应用/共享服务趋势和模型调用计数；
短时验证通过不等于已修复底层泄漏。
